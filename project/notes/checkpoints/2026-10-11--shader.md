# Learning checkpoint – Shader jako samostatná odpovědnost

**Datum:** 2026-10-11  
**Navazuje na code commit:** `caf3251779806690cc95fd722851947e8bc89183`

## Kontext etapy

Po oddělení `Application` a `Model` byla z původní pomocné funkce z `cv02` vyčleněna třída `Shader`.

Aktuální odpovědnost `Shader` je úzká:

- vytvořit jeden OpenGL shader objekt,
- načíst jeho GLSL zdroj ze souboru,
- předat zdroj OpenGL,
- shader zkompilovat,
- zkontrolovat výsledek kompilace,
- uchovat ID výsledného kompilovaného shaderu.

`ShaderProgram` zatím implementovaný není.

## Samostatně prokázáno

- Na základě dohodnutého rozhraní jsem převedl původní procedurální kompilaci shaderu do samostatné třídy a zapojil `Shader.cpp` do CMake.
- Výsledný objekt ukládá pouze OpenGL shader ID; data potřebná jen při konstrukci nejsou zbytečně uchovávána jako členský stav.

## Pochopeno s vedením

- Rozlišení mezi trvalým stavem objektu a dočasnými údaji potřebnými pouze při konstrukci:
  - trvalý stav: `GLuint id`,
  - dočasné: `shaderType`, cesta k souboru, text zdroje, compile status a error log.
- Význam sekvence:
  `glCreateShader → glShaderSource → glCompileShader → glGetShaderiv / glGetShaderInfoLog`.
- Použití member initializer listu pro inicializaci `id`.
- Bylo upozorněno na nedosažitelný kód po `exit(EXIT_FAILURE)`; v následném commitu byl odstraněn.

## Vývoj pochopení

Původní kód měl kompilaci shaderu jako volnou pomocnou funkci. Po refaktoringu už není shader vnímán jen jako několik OpenGL příkazů, ale jako samostatný prostředek s vlastní odpovědností a vlastním OpenGL handlem.

Důležité je, že objekt nemusí uchovávat vše, co se při jeho vytvoření použilo. Cesta k souboru a source code jsou potřeba pro vytvoření shaderu, ale po úspěšné kompilaci je pro další krok – linkování do programu – zásadní především jeho OpenGL ID.

## Potřebuje upevnit

- Životní cyklus shader objektu: kdy lze zavolat `glDeleteShader` po jeho připojení a slinkování do `ShaderProgram`.
- RAII řešení destrukce zatím není implementované.
- `createShaderFromFile` je nyní privátní členská metoda, přestože nepoužívá stav instance; zda ji ponechat takto, udělat `static`, nebo přesunout na jinou pomocnou úroveň zatím není důležité pro DU1.
- Způsob propagace chyb je zatím jednoduchý přes `exit(EXIT_FAILURE)`; robustnější návrh zatím nebyl řešen.
- `ShaderProgram` a vztah mezi jednotlivými shadery a slinkovaným programem je zatím nevyhodnocen v implementaci.

## Další procvičení

1. Navrhnout konstruktor `ShaderProgram` tak, aby dostal objekty `Shader`, ne holá ID z `Application`.
2. Vysvětlit rozdíl mezi kompilací jednotlivého shaderu a linkováním shader programu.
3. Po úspěšném linkování rozhodnout, kdo a kdy zruší jednotlivé shader objekty.
4. Doplnit `use()` do `ShaderProgram` a obhájit, proč vyšší vrstva rozhoduje kdy program použít, zatímco program zná jak se aktivovat.
